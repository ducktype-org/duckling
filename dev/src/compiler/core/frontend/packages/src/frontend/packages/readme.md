# Frontend Packages

Resolved package metadata used by the rest of the frontend: package id,
import name, version, feature flags and the list of direct dependencies
(with their aliases). Built from manifest input (`RawPackageInfo`) and
stored in global compiler state, then accessed from queries through
`*AccessLocked` wrappers that participate in the incremental query
framework.

## Package id and name

- The **id** uniquely identifies a package. It is a part of mangled symbol
  names, so it must match `[A-Za-z_][A-Za-z0-9_]*` (`isValidPackageID`,
  checked by `createPackageInfo`). Ids generated by the compiler (from file
  names, random strings, the language server) go through `sanitizePackageID`.
- The **name** is the import name of the package: the default alias of a
  dependency on it, and the name under which a package can import itself.
  Names are never used in symbol names, so renaming a package does not
  change the symbols of its code.

## Why locks (`*AccessLocked`)

The compiler is **query-based and incremental**. Anything a query reads
must be turned into a tracked dependency, so that when a value changes
the query is invalidated and re-run on the next build. For packages, the
inputs that can change between builds are:

- whether a given package exists at all (id + identity),
- the **name** of a package (same id, different import name),
- the **size** of its dependency list (something added/removed),
- a specific `(package, alias) → target package id` lookup result
  (alias added, removed, or repointed),
- a specific lookup of a package by id (package added or removed).

> `version` and `features` are **not tracked** currently (see #2668) —
> generated code may eventually depend on them (feature-gated APIs,
> version conditionals), at which point reads will need to register the
> dependency.

The relevant side inputs:

| AccessLocked                               | Side input registered on `unlock`            |
|--------------------------------------------|-----------------------------------------------|
| `PackageAccessLocked`                      | `QueryPackageSideInput` (key: package hash)   |
| `PackageNameAccessLocked`                  | `QueryPackageNameSideInput` (key: id + name)  |
| `PackageDependenciesAccessLocked`          | `QueryPackageDependencyCountSideInput`        |
| `PackageDependencyAliasAccessLocked`       | `QueryPackageDependencyAliasSideInput` (alias outcome is part of the key) |
| `PackageLookupAccessLocked`                | `QueryPackageLookupSideInput` (lookup outcome is part of the key) |

Because the alias and lookup side-inputs encode the *outcome* in their key,
distinct results are tracked as independent edges — flipping an alias from
missing → present, repointing it to another package, or a package with a
looked-up id appearing (e.g. switching from `--no-std` to std) correctly
invalidates dependents. Such outcomes cannot be enumerated from the current
packages alone (a failed lookup may be for any name), so their keys are
stored as metadata and re-validated by `collectPackageInputData` when the
driver (or the language server) collects the inputs of a new build.

## How a manifest entry becomes a `PackageInfo`

1. Driver reads the manifest JSON.
2. `RawPackageInfo::fromJson` produces a `RawPackageInfo` (validates the
   shape, reports diagnostics). The driver then verifies the whole manifest
   (`PackageCompilationManifest::verify`): unique ids and names, known
   dependencies, and unique dependency aliases within a package.
3. `createPackageInfo(raw, all_package, report)` validates the package id,
   loads the module tree under `package_path` and constructs a `PackageInfo`.
4. The `PackageInfo` is stored in global state and looked up by id from
   queries via `PackageAccessLocked` / `PackageLookupAccessLocked`.

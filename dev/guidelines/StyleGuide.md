# General

In general we follow the style generated by `clang-format`
using [.clang-format](../.clang-format) configuration file.

To call clang format on do:
```shell
$ cd dev
$ clang-format -style=file -i path/to/file.cpp
$ # formatting all files in folder:
$ find path/to/folder \( -iname *.hpp -o -iname *.cpp \) | xargs clang-format -style=file -i
```

# Additional rules

## Basic Formatting

* Indentation
  * Use tabs for indentation
  * Use spaces to align horizontally

* Lines shouldn't generally be longer than `100` characters

* Avoid more then 3 levels of indentation in a function

* Everything that can be hidden should be hidden. For example local functions in anonymous namespaces or private members in class.

## TODO, FIXME, ...

Mark places in code as follows:

* `@TODO:` - To be done (functionality doesn't yet exists)
* `@FIXME:` - To be fixed (functionality exits but is bugged/incorrect)
* `@IDEA:` - Any idea for change or addition in the code
* `@AnyOtherSimilarMarking:` - Remember to use `@`-sign, so it can be easily found in the future

## Comments

* Use English
* Add single space at the beginning of a comment
* Place comments before the commented part
* Use only one line comments for code explanations

~~~cpp
// like this
~~~

Only multi line comments as function documentation
~~~cpp
/**
 * some documentation
 * some more documentation
 */
function
~~~
Avoid commenting out code 

## Naming scheme

Language: English 
Names should be meaningful, apart from knows exertions like `i`, `j`.

* Types/Classes: PascalCase
* Constants, Macros: CAPITAL_CASE
* Variables: snake_case
* Functions: camelCase
* Other: camelCase

~~~cpp
class Dog: public Animal, public Friend {
~~~

~~~cpp
for (int i = 0; i < n; i++) {
~~~
<br>After every `#include`
<br>No space after `template`

## Spiting lines into multiple

This is generally covered by `clang-format`, but might sometimes produce strange results,
so manual formatting might be necessary (but try to avoid it, sometimes change in format configuration may be better).

**Important**: Trailing commas can strongly influence `clang-format`, and will often multiline formatting.

When formatting manually try to follow rules:

* Use common sense, and care for readability
* Put newlines after comma, colon or opening parenthesis
* If newline is present after opening parenthesis put closing parenthesis alone in new line
* If split is on a list of thing it's better to split them all into separate lines to keep structure
* See how other lines are formatted by clang

Example:

~~~cpp
veryVeryExtremelyLongFunction(
    someLongVariable,
    someOtherLongVariable &&
        anotherLongVariable,
    shorter + shorter,
    LongishFunction()       
);
~~~

## Code blocks

Opening brackets in code blocks are always at the end of first line after a space

~~~cpp
if (value) {
    doSomething();
}
~~~

In flow control single line code blocks cannot have brackets.
Code block without brackets can only be placed on the same line as flow control statement.

~~~cpp
for (value: values) doSomething(value);
~~~

## If-Else

<!-- `else` or `else if` in line after single line `if` or after closing bracket and a space after non-single line `if` -->

If `else` or `else if` is present use brackets. Here an exception can be made
and same line codeblock can be used. 

~~~cpp
if (coffee) {
    work();
    sleep();
} 
else if(tired) { sleep(); }
else {
    lieDown();
    cry();
}

~~~

## Block sections

Write block sections `public`, `private`, `case X`, `default` etc. at the same level as their blocks definition.

~~~cpp
class Star {
public:
    int32_t brightness = 0;
private:
    int32_t mass;
};

switch (place) {
case 1:
case 2:
case 3:
default:
    cout << "congratulations\n";
}
~~~

## Types

* Use fixed width length integers ie `int32_t`, and never `int`, `long`.
* Use references instead of pointers when possible.
* Use `const`, `constexpr`, `constinit` when possible.
* Always add parenthesis around dereference `(*pointer)`.

## Classes

* Use true virtual classes with `=0` and `override`.
* Use `final` and `override`.
